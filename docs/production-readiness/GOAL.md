# GOAL — Hotel Metasearch Production-Readiness Mission

**Полная версия ТЗ (эталон, байт-в-байт):** `docs/production-readiness/MISSION-SPEC.md`
(sha256 `20dd46eaa0ff4e6058c4e638de1c8cbb9efc4e8cfe1f3ca4cf6ae77afb8791b5`, 82 284 байта).
При любом расхождении побеждает MISSION-SPEC.md. Этот файл — рабочая карта требований.

## Главная цель

Довести существующий hotel metasearch до качественного, быстрого, надёжного и функционально
законченного MVP. Не аудит и отчёт, а самостоятельные: диагностика → доказательство
первопричины → минимальное изменение → regression test → коммит → live-проверка → документация.

Целевой сценарий: город + даты + взрослые/дети → «Найти отели» → быстрые корректные результаты
из Trip.com и СравниОтеля параллельно; одинаковые отели объединены, предложения не теряются,
карточки единообразны, питание/удобства/приватность определяются максимально полно,
расстояния корректны, все кнопки/фильтры/сортировки работают.

**Приоритеты:** достоверность данных → полнота результатов → сохранность состояния →
функциональная корректность → скорость → качество кода → косметика.
Никаких выдуманных данных ради красоты выдачи. Не объявлять готовность раньше времени.

## Обязательные инварианты

1. **Trip.com только в headed Chromium** (`headless=False`) для всех реальных поисков,
   навигаций, rate-задач, восстановления и авторизованных профилей. Headless на реальном
   пути Trip.com категорически запрещён, включая fallback после ошибки запуска. Headless
   допустим только в независимых локальных UI-тестах. Нужны регрессионные проверки
   конфигурации launch.
2. **Git-дисциплина:** targeted tests → проверка diff → явный список файлов в `git add` →
   отдельный содержательный коммит → обновление STATUS.md (+DECISIONS.md) после каждого
   логического изменения. Не коммитить недоказанное. Не переписывать историю, никаких
   фиктивных коммитов. Пушить проверенное.
3. **Изоляция БД:** все пишущие тесты/диагностика — только с явным изолированным
   `HOT_TICKETS_DB_PATH`. Запрет на загрязнение production-БД. Не коммитить БД, профили,
   cookies, токены, секреты.
4. **Честность статусов:** ok / partial / blocked / timeout / unavailable отражают реальность.
   HTTP 200 ≠ успех. Никаких fake success, подмены ошибок, «неизвестно» за «подтверждено».
   Антибот/CAPTCHA не обходить.
5. **Запрет скриншотов и визуального анализа** (ТЗ п.20): только DOM/тексты/атрибуты/сеть/
   события/console/логи/API/метрики. Не обходить через субагентов.
6. **Не трогать чужую работу:** не откатывать и не перезаписывать непонятные изменения;
   mass-rollback — не инструмент. При рискованной правке — контрольная точка.

## Постоянная память проекта

- `GOAL.md` (этот файл) — требования.
- `STATUS.md` — факт-состояние: фаза, задачи (TODO/IN PROGRESS/BLOCKED/DONE/NOT VERIFIED),
  подтверждённые результаты, метрики до/после, коммиты, субагенты, блокеры, следующий шаг.
  DONE = проверено. Код без подтверждения — NOT VERIFIED.
- `DECISIONS.md` — техническая память: доказанные первопричины, воспроизведения,
  эксперименты (удачные и нет), архитектурные решения, ограничения источников.
- При потере контекста: сначала перечитать эти три файла, затем Git/файлы/процессы.
  Документация не авторитетнее репозитория: противоречие → проверять фактами.

## Ключевые функциональные требования

- **Поиск (п.5):** параллельные источники; прогрессивный рендеринг без ожидания всех 400;
  город/даты/гости/возраст детей; пагинация и лимиты; статусы честные; отмена/повтор/
  восстановление; отказ одного источника не рушит другой; устаревшие ответы не трогают
  новый поиск.
- **Карточки (п.6):** единая модель и рендеринг; все доступные варианты номеров и тарифов
  от обоих источников (сейчас Trip показывает альтернативы, Sravni — нет: выяснить, что
  реально даёт API); matching без слияния разных отелей и без потери офферов; сохранение
  валюты/периода/питания/отмены/ссылок.
- **География (п.7):** центр города, настоящее метро (если есть), настоящий пляж (если есть).
  Дананг: починить расстояния до пляжа, исправив общий алгоритм, не город-специфичный костыль.
  Река/озеро/канал/порт/пристань ≠ пляж; автобусная остановка ≠ метро. Статусы геоданных
  различать (подтверждено / не найдено / неприменимо / в обработке / сервис недоступен /
  не подтверждено). Overpass-ошибка ≠ «нет пляжа». Персистентность geo_id и terminal geo jobs
  без бесконечных повторов.
- **Питание и удобства (п.8):** максимальный подтверждённый охват (без выдумывания):
  RO/BB/доп. плата/HB/FB/AI/иные/неизвестно; питание оффера vs отдельно; удобства с отличием
  «отсутствует» от «неизвестно». Не выводить питание из названия/звёзд.
- **«Личный номер» (п.9):** приватность = отдельное пространство; койко-место/dormitory не
  личный; неизвестно ≠ личный. Regression-тесты на приватные/общие/неизвестные.
- **Отзывы (п.10):** неработающая кнопка отзывов Sravni → реальный URL; нет URL — не имитировать.
  Инвентаризация всех фильтров/сортировок/кнопок: каждый активный элемент обязан работать.
- **Цены (п.11):** соответствие датам и составу гостей; не смешивать ночь/период, гостя/группу,
  валюты, включённое/доплаты, разные номера/условия. Не суммировать разные офферы.
- **Производительность (п.12):** измеренные bottlenecks по конвейеру; ранние первые карточки;
  прогрессивность корректна; не поднимать concurrency без проверки; рефакторинг не ради
  эстетики.

## Обязательные live-проверки (п.13–14)

Города: Дананг (пляжи, без метро), Париж (метро, без морских пляжей), приморский с метро
и пляжами, город без метро и пляжей, + дополнительные. Составы гостей, даты, лимиты,
matching, все фильтры. Отказы: недоступность каждого источника, Overpass, параллельные
поиски, отмена, поздние ответы, перезапуск процесса, восстановление задач, отсутствие
SQL locking, отсутствие утечек, terminal jobs не повторяются.

Три вида smoke: **progressive** (ранние карточки, счётчики, без incomplete cards),
**full-completion** (штатное завершение: без необъяснённых queued/running; объяснить все
расхождения hotels/cards/canonical/DOM/offers; инвариант discovered = ready + pending + unusable),
**failure/cancellation** (отмена, закрытие клиента, отказы, перезапуск, сохранность).

## Flaky-тесты (п.16)

`test_beach_search_uses_city_and_country_slugs` / `IndexError` в
`test_hotel_search.py:2292` / фикстура `tests/conftest.py`: проверить актуальную
первопричину; текущее восстановление через `.update()` неточно (остаются новые элементы) —
исправить на точное восстановление с удалением добавленного, try/finally; проверить все
общие глобальные состояния; не чинить flaky удалением тестов/ослаблением assertions/снами.
Regression-тесты: воспроизводимость, отсутствие утечки, точное восстановление, кэши в
production-коде работают. Многократные прогоны после фикса.

Примечание (2026-10-14, аудит воспроизводимости): исходник `test_hotel_search.py` (~4460
строк) утрачен до публикации репозитория (root-коммит уже содержит bytecode-загрузчик);
исполняемая копия preserved-тестов существует только как архив
`fixtures/hotel_search_test_module.cpython-312.pyc.gz` (теперь tracked в git, пин sha256 —
`tests/test_preserved_test_archive.py`). Ссылка `test_hotel_search.py:2292` выше относится
к утраченному исходнику (строка сохранена в байткоде), а не к текущему 345-строчному
загрузчику.

## Geo-кэш между процессами (п.17)

Штатный запуск передаёт `HOT_TICKETS_DB_PATH`; geo_id сохраняется и читается после
перезапуска; кэш различает подтверждённое/неизвестное; обновление при изменении; тесты
не пишут в prod-БД. Подтвердить кросс-процессно на рабочей конфигурации.

## Субагенты (п.18)

Узкие независимые задачи, границы, критерии, бюджет; мониторинг реального прогресса
(диффы/тесты/коммиты, не статус running) каждые ~5–10 минут; остановка зависших;
интеграция только после проверки; главный отвечает за коммиты; не терять полезную работу.

## Критерии готовности (п.22)

Функциональность (мультисити, параллельность, headed-only, изоляция отказов, полнота,
единые карточки, корректные цены, питание/удобства, приватность, расстояния, рабочие
кнопки) + Надёжность (нет необъяснённых flaky, потерь, маскировок, SQLite locking,
загрязнений, утечек; контролируемая деградация; harness чист; exit codes по контракту) +
Производительность (измерено, оптимизировано без потерь, воспроизводимо, прогрессивно,
headed не подменён) + Техническая сохранность (pytest/compileall/node, integrity/FK,
регрессии, коммиты, документация, remote совпадает). Вердикт `PRODUCTION READY` — только
по выполненным критериям; внешние ограничения фиксировать честно.

## Бюджет остановки

Работать до выполнения критериев либо до объективных внешних блокеров, зафиксированных
с доказательствами. Не задавать вопросов, ответимых из кода/логов/тестов.
