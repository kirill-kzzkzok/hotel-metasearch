## D1. Flaky beach-тест `test_beach_search_uses_city_and_country_slugs` (2026-10-13)

- **Факт:** падал ~9/10 в пределах одного файла `tests/test_hotel_search.py`, проходил
  изолированно. `IndexError` в `test_hotel_search.py:2292` = `calls[1]` (тест ждёт **два**
  photon-запроса; в наборе приходил один).
- **Первопричина (доказано):** модульно-глобальные кэши протекали между тестами процесса.
  `PHOTON_CITY_EXTENTS` (providers) греется любым ранним тестом, резолвящим тот же город →
  первый photon-запрос исчезает → `calls[1]` IndexError. Плюс глобальные Overpass-состояния
  (`_OVERPASS_ENDPOINT_COOLDOWNS`, failure streaks, `_OVERPASS_NEXT_START_AT`,
  `_OVERPASS_COOLDOWN_UNTIL`) от транспортных тестов: `_OverpassRequestDeferred` (наследник
  TimeoutError) глотается `_overpass_beach_features` → overpass-вызов исчезает.
- **Фикс:** `tests/conftest.py` autouse-фикстура: сохраняет и очищает globals до теста,
  восстанавливает после.
- **Результат:** 6/6 прогона файла, 3 полных набора 618 passed.
- **Открытый дефект (ТЗ п.16):** восстановление через `.update(saved)` неточно — элементы,
  добавленные самим тестом, остаются после teardown. Нужен точный rollback (очистка + запись
  ровно сохранённых). Оставлено как задача 2 реестра.
- **Закрыто:** задача 2 → `8e6c075` (точный rollback из снапшота + try/finally, фаза 2).

## D10. Exit code 3 сервера в smoke — контракт, не дефект (2026-10-14)

- **Механика:** harness шлёт `CTRL_BREAK_EVENT` в process group сервера; uvicorn на Windows
  обрабатывает SIGBREAK как graceful shutdown («Application shutdown complete. Finished
  server process» в логах), после чего процесс завершается с кодом 3 (Windows console
  control-event exit). Порты освобождаются, БД остаётся целой (integrity ok).
- **Вывод:** `server_exit_code: 3` в smoke-артефактах = штатное внешнее завершение.
  Дефектом не считать; менять код выхода ради «зелёного» отчёта не нужно (спека §15).

## D15. Rate fast-path: in-page rate endpoint вместо detail-страниц (2026-10-14, `dd849fd`)

- **Причина падения fast-path в сервере (а standalone работал):** (1) `Page.evaluate:
  Execution context was destroyed` — detail-страница Trip.com продолжает клиентски
  навигироваться после goto, убивая контекст при установке шаблона; фикс — возврат на
  стабильную домашнюю страницу до установки `window.__rateTemplate` и fetch-ей.
  (2) Анонимный scratch-профиль получает `htlSpiderActionErrorCode 4030` на
  rate-endpoint — а залогиненный профиль (ручной логин пользователя) проходит.
- **Решение:** fast-path вызывает собственный rate-endpoint сайта
  (`getHotelRoomListOversea` — тот же, что вызывает detail-страница) через in-page
  fetch: один персистентный контекст, одна detail-навигация для захвата шаблона
  запроса, затем N fetch-ей с подстановкой hotelId. Sentinel при защите → fallback
  на detail-пул (merge позиционный по порядку задач).
- **Живое доказательство (rate-pool smoke, 12 trip-отелей):** 12/12 `ok` через
  fast-path; 0 `in_page_fetch_failed`; 0 detail-page fallback; 296 room-rate
  наблюдений с реальными данными (типы номеров, цены RUB, питание, отмена);
  средняя **1.2с/отель** против 15–20с на detail-страницу. 663 теста зелёные.
- **ТЗ-требование выполнено:** тарифы получаются БЕЗ последовательного открытия
  detail-страниц; detail-пул остаётся только как fallback при реальной защите.

## D16. Fast-path fallback по статусам + защита не ретраится detail-страницами (2026-10-14)

- **Дефект (аудит):** fallback-решение в `rate_enrichment.py` сравнивало ДЛИНУ результата
  (`len(enriched) != len(tasks)`), а fast-path после protection-break возвращает список полной
  длины со стабами `not_started` → detail-fallback не запускался, заблокированный отель не
  персистился (строка оставалась `queued`), вопреки докстрингу.
- **Решение:** (1) fallback-решение по СТАТУСАМ (`not_started`-стабы → remaining);
  (2) blocked-отель персистится до break (on_result внутри ветки защиты, с `rate_status`);
  (3) при явной защите (spider/401/403/429/430) detail-fallback НЕ запускается — повторная
  навигация к тому же источнику только усугубит блокировку (GOAL-контракт: не обходить
  антибот); при sentinel (шаблон не захвачен) и исключении fast-path — fallback запускается
  для недостигнутых; (4) перевод индексов subset→full task order (legacy-пул отчитывается
  индексами своего входа) — иначе частичный fallback персистил бы исходы под чужим отелем;
  (5) при исключении fast-path уже персистённые исходы восстанавливаются из
  `persisted_outcomes` и исключаются из fallback (нет двойного сбора); (6) queued-строки
  пишутся только после взятия profile-лока (проигравший гонку browser_busy не оставляет
  свежих queued-строк поверх терминальных победителя).
- **Дополнительно:** гейт fast-path вынесен в `_tripcom_rate_fast_path_enabled()` — pytest
  пересоздаёт `PYTEST_CURRENT_TEST` в каждой фазе, env-подмена из фикстуры не работала;
  тесты подменяют функцию напрямую.
- **Regression-тесты:** `tests/test_hotel_rate_fastpath_fallback.py` — 9 тестов (защита →
  нет fallback; sentinel/исключение → fallback недостигнутых; частичный успех; merge без
  source_hotel_id; перевод индексов; blocked персистится терминально; отсутствие дублей
  наблюдений при повторном persist).
- **Воспроизводимость тестов (закрытие аудита):** `fixtures/hotel_search_test_module.cpython-312.pyc.gz`
  — единственная сохранившаяся копия preserved-тестов (исходник утрачен до публикации,
  root-коммит уже с loader'ом; git-история и бэкапы проверены). Фикстура закоммичена в git
  (tracked, `.gitignore` на tracked не действует), пин sha256 в
  `tests/test_preserved_test_archive.py`, guard-сообщение лоадера при отсутствии файла.
  Чистый клон: 187 тестов собираются, файл больше не untracked-зависимость.

## D19. Стейджированный nearby-lookup Overpass (2026-10-15, `6a940c2`)

- **Дефект:** `_osm_nearby_features` делал ОДИН запрос 5 категорий с
  `around:8000` и дедлайном 3 с (дефолт; beach-геометрия имела 12 с). При
  нагруженном Overpass: 0/7 успеха на полный запрос, 2/2 на metro-only 2 км —
  метро-дистанция карточек (главная nearby-фича) глохла за тяжёлым
  landmark-набором, а медленные ответы нельзя было получить физически.
- **Решение:** два стейджа — (1) метро `around:2000` (осмысленный радиус
  «до метро»), (2) fail-safe wide `around:8000` (аэропорт/достопримечательности);
  дедлайн 12 с обоим; падение стейджа 2 сохраняет результат стейджа 1;
  терминальный `source_unavailable` только при падении обоих (короткий TTL
  1 мин сохранён).
- **Живые доказательства:** (а) прямой вызов приложения — `metro=Mornington
  Crescent 2.979 km` при ReadTimeout wide-стейджа; (б) сквозной Париж-смоук —
  строки метро на карточках («🚇 262 м до метро»), покрытие 82.2% при живом
  flapping; (в) регресс-тесты: stage-survival, both-dead terminal,
  per-stage радиусы/селекторы.
- **Ограничение (внешнее):** 95%+ покрытие §6 достижимо только при здоровом
  Overpass; при flapping честно деградирует (unknown + retry). Утро стабильнее
  (известно по памяти сессии), краткосрочный error-TTL обеспечивает самозалечивание.
